# 自主建模中的工具消息配对

2026-10-18 的一次自主建模在完成四次比较后收到模型接口 HTTP 400，原因是
`tool` 消息没有对应的 `tool_calls`。原始检查点中的有效工具调用编号均有回复，
问题发生在发送给模型前的消息整理阶段。

真实记录的隔离回放确认：模型返回了不完整的 `nir_submit_decision` 参数；
通用 DanglingToolCallMiddleware 为未执行的调用补充失败 ToolMessage。
随后自主工作流移除了损坏调用的参数和编号，却保留失败回复，导致请求不合法。
这里的失败回复只表示解析失败，不证明任何决策被接受或工具被执行。

`decision_provider.malformed_call_message_view` 现在在仅供模型使用的消息副本中，
成对处理无效调用和同一助手批次中的对应回复，保留已有解析纠正提醒。
批次边界以助手消息为准，另一个有效批次复用同一传输编号时，其回复继续保留。
有效调用、同批有效/无效调用混合的记录、其他工具和原始持久消息均不改写。
该投影也覆盖首个决策上下文之前的解析失败。

错误提示按照可信停止来源区分服务调用失败、决策解析失败、执行异常、重复操作
与运行额度耗尽，不再将所有失败都显示为“达到运行限制”。

回归验证通过实际 DeepSeek 适配器构造请求并检查连续调用/回复关系，不发出外部
请求。同步和异步 Lead 测试组合真实的 Dangling 与 NIR 中间件，覆盖纠正后继续
交付，以及纠正次数耗尽后持久停止。无效 JSON 不被修补成可执行决策；重试次数、
预算、最终 Test 封存、模型选择、人工审批和模型入库规则均保持原样。

历史失败任务不自动续跑或重训，既有结果、划分和原始检查点保持不变。
